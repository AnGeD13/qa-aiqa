# Матрица трассировки автотестов — PomidorQA

**Цель:** связать требования из [`requirements.md`](requirements.md) с автотестами и видеть, какие проверки уже автоматизированы, а какие остаются пробелом.

**Область:** функциональные требования PomidorQA (регистрация и вход, профиль, навыки, слоты, каталог, бронирование, отмена, «Мои встречи»). Вне области: пункты из раздела «Не входит в MVP».

**Дата актуализации:** 2026-09-24

**Приоритеты:** P0 — блокирует основной путь или целостность бронирований; P1 — влияет на функциональность; P2 — детали поведения и отображения.

**Колонка «Уровень»:** уровень пирамиды, на котором проверка закрывается — `unit` (чистая логика без сети и браузера), `API` (запрос к серверу без интерфейса), `E2E` (реальный браузер). У каждой проверки ровно один уровень: тот, на котором дефект ловится дешевле всего. Пока автотеста нет, указан планируемый уровень.

**Колонка «Автотест»:** ссылка на spec-файл, если проверка автоматизирована, и `—`, если автотеста пока нет.

| **Итого** | **61** | **10** |

Unit и API в таблице почти пустые не потому, что эти проверки не нужны, а потому что к исходному коду и внутреннему API PomidorQA доступа нет: тестируем чёрный ящик на живом стенде. Без кода продукта нельзя вызвать доменные функции напрямую и нельзя честно закрыть контракт сервера запросом к реальному API. Поэтому в колонке «Уровень» unit и API остаются *планируемыми*: так дешевле ловить дефект, если код когда-нибудь появится. Пока закрываем эти проверки снаружи через E2E. Учебные spec в `tests/unit` и `tests/api` бьют в локальные моки из `pyramid-mocks/`, а не в продукт — в этой матрице они покрытие не считают (см. правило про `API (мок)` и `unit (мок)` ниже).

## Как поддерживать матрицу

1. Новый автотест — заменить `—` на ссылку вида `[booking-flow.spec.ts](tests/e2e/booking-flow.spec.ts)`.
2. Один автотест может закрывать несколько строк — тогда ссылка повторяется в каждой из них.
3. Новое требование в [`requirements.md`](requirements.md) — добавить строку со статусом `—`, чтобы пробел был виден.
4. Уровень указывается в колонке «Уровень» у каждой проверки, а не только у автоматизированных: одно значение из `unit`, `API` или `E2E`. Если проверку автоматизировали на другом уровне, чем планировали, значение меняется вместе с добавлением ссылки.
5. Автотест, который бьёт в локальный мок-сервер, а не в живой стенд, указывается как `API (мок)`, а unit-тест учебной функции из `pyramid-mocks/` — как `unit (мок)`. Иначе матрица утверждает, что продукт проверен, хотя проверена учебная реализация. Такие строки в «Покрытие по уровням» автоматизированными не считаются.
6. Таблицу «Покрытие по уровням» пересчитывать при каждом изменении набора строк или появлении нового автотеста.
