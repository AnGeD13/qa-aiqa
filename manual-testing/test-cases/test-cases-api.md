# Тест-кейсы API "Пиццаед"

**Цель:** проверка контракта эндпоинтов `/api/course/v1/shop/*`: коды ответов, фильтрация товаров, границы количества в корзине, создание заказа и изоляция учебных сессий.

**Область проверки:** пункты приоритетов P0 и P1 из [`checklist-pizzaed.md`](../checklists/checklist-pizzaed.md). UI-кейсы вынесены в [`test-cases-ui.md`](test-cases-ui.md). Пункты приоритета P2 в набор не входят.

**Окружение:** учебный стенд «Пиццаед», базовый путь `/api/course/v1/shop`. Инструмент отправки запросов — Postman или аналог.

**Дата актуализации:** 2026-09-10

**Соглашения по данным:**

- Все запросы выполняются с заголовком `X-Course-Session`; значение уникально для прогона и обозначается как `S1`, второе значение — `S2`.
- Пути кейсов приведены сокращённо, без префикса `/api/course/v1`.
- *Товар A* — доступный товар; *Чизкейк* — эталонный товар не в наличии; `{id_A}` и `{id_cheesecake}` — их идентификаторы.
- Коды ответов, не зафиксированные в требованиях, помечены ссылкой на вопрос из [`open-questions.md`](../../docs/open-questions.md) и фиксируются как фактический контракт.

## Товары

### TC-API-PROD-01. Получение списка товаров

**Покрывает:** CL-API-PROD-1 | **Приоритет:** P0

**Предусловия:** сессия `S1` определена.

**Шаги:**

1. Выполнить `GET /shop/products` с заголовком `X-Course-Session: S1`.
2. Проверить код ответа.
3. Проверить структуру элементов списка.

**Ожидаемый результат:** код 200, тело содержит непустой список товаров, каждый элемент включает идентификатор, название, категорию, описание, цену, рейтинг, бейджи и признак наличия.

**Обоснование:** базовый контракт каталога, от которого зависят все UI-проверки и последующие API-кейсы. Неполная структура элемента ломает отображение карточки товара.

### TC-API-PROD-02. Поиск товаров параметром q

**Покрывает:** CL-API-PROD-2 | **Приоритет:** P1

**Предусловия:** сессия `S1` определена.

**Шаги:**

1. Выполнить `GET /shop/products?q=соус`.
2. Проверить код ответа и состав списка.
3. Проверить категории найденных товаров.
4. Выполнить `GET /shop/products?q=zzzqwerty` и проверить ответ.

**Ожидаемый результат:** код 200. Для запроса «соус» возвращаются товары с совпадением по названию, описанию или бейджам, в том числе из разных категорий. Для заведомо отсутствующей строки возвращается пустой список, а не ошибка.

**Обоснование:** серверная реализация поиска — источник данных для UI. Пустая выдача должна оставаться корректным ответом 200, иначе клиент показывает ошибку вместо сообщения об отсутствии результатов.

### TC-API-PROD-03. Фильтрация товаров параметром category

**Покрывает:** CL-API-PROD-3, CL-API-PROD-6, Q-18 | **Приоритет:** P1

**Предусловия:** известны допустимые значения параметра `category`.

**Шаги:** выполнить запрос из таблицы и проверить код ответа и состав списка.

| Вариант | Запрос | Ожидаемый результат |
|---|---|---|
| 1 | `GET /shop/products?category=<существующая>` | 200, только товары этой категории |
| 2 | `GET /shop/products?category=zzz` | 200 и пустой список, ошибка сервера отсутствует |
| 3 | `GET /shop/products?category=` | 200, поведение фиксируется как контракт |

**Ожидаемый результат:** соответствует таблице; ответ 5xx недопустим ни в одном варианте.

**Обоснование:** требования не описывают реакцию на несуществующую категорию (Q-18). Некорректная обработка неизвестного значения — типовая причина ошибки 500 на публичном эндпоинте.

### TC-API-PROD-04. Фильтрация по наличию параметром in_stock

**Покрывает:** CL-API-PROD-4, Q-18 | **Приоритет:** P1

**Предусловия:** в данных есть и доступные товары, и «Чизкейк».

**Шаги:**

1. Выполнить `GET /shop/products?in_stock=true` и проверить признак наличия у всех элементов.
2. Выполнить `GET /shop/products?in_stock=false` и проверить состав списка.

**Ожидаемый результат:** код 200. При `true` все товары доступны и «Чизкейк» отсутствует; при `false` возвращаются только недоступные товары, включая «Чизкейк».

**Обоснование:** параметр используется автотестами для подготовки данных. Инвертированная или игнорируемая фильтрация приводит к попыткам добавить в корзину заведомо недоступный товар.

### TC-API-PROD-05. Одновременная передача q и category

**Покрывает:** CL-API-PROD-5, Q-19 | **Приоритет:** P1

**Предусловия:** подобрана пара «категория и поисковое слово», дающая непустое пересечение.

**Шаги:**

1. Выполнить `GET /shop/products?q=соус&category=<категория>`.
2. Проверить код ответа и состав списка.

**Ожидаемый результат:** код 200. Результат соответствует принятой трактовке Q-19 — параметры применяются одновременно как логическое И; фактическое поведение фиксируется как контракт.

**Обоснование:** для UI требование задаёт приоритет поиска над категорией, для API правило не описано. Расхождение уровней приводит к разному поведению ручных и автоматизированных проверок.

### TC-API-PROD-06. Получение товара по идентификатору

**Покрывает:** CL-API-PROD-7 | **Приоритет:** P0

**Предусловия:** известен `{id_A}`.

**Шаги:**

1. Выполнить `GET /shop/products/{id_A}`.
2. Проверить код ответа.
3. Сравнить поля товара с данными из списка каталога.

**Ожидаемый результат:** код 200, возвращён один товар, поля совпадают с данными из `GET /shop/products`.

**Обоснование:** контракт карточки товара. Расхождение данных списка и карточки означает, что пользователь принимает решение о заказе по неактуальным данным.

### TC-API-PROD-07. Запрос несуществующего и некорректного идентификатора товара

**Покрывает:** CL-API-PROD-8, CL-API-PROD-9 | **Приоритет:** P0

**Предусловия:** сессия `S1` определена.

**Шаги:** выполнить запрос из таблицы и проверить код ответа.

| Вариант | Запрос | Ожидаемый код |
|---|---|---|
| 1 | `GET /shop/products/999999` | 404 |
| 2 | `GET /shop/products/abc` | 404 или 422, ответ 5xx недопустим |
| 3 | `GET /shop/products/-1` | 404 или 422, ответ 5xx недопустим |

**Ожидаемый результат:** для несуществующего числового идентификатора возвращается 404, как задано требованием. Для нечисловых и отрицательных значений сервер отвечает корректным клиентским кодом без внутренней ошибки.

**Обоснование:** код 404 зафиксирован требованием прямо. Некорректный тип идентификатора проверяется отдельно, так как приведение типа без валидации — частая причина необработанного исключения.

## Корзина

### TC-API-CART-01. Добавление доступного товара в корзину

**Покрывает:** CL-API-CART-1 | **Приоритет:** P0

**Предусловия:** корзина сессии `S1` пуста, известен `{id_A}`.

**Шаги:**

1. Выполнить `POST /shop/cart` с телом, содержащим `{id_A}` и количество 1.
2. Проверить код ответа.
3. Выполнить `GET /shop/cart` и проверить состав.

**Ожидаемый результат:** код 201, корзина содержит одну позицию с Товаром A в количестве 1.

**Обоснование:** код 201 зафиксирован требованием прямо. Кейс создаёт предусловие для всех остальных проверок корзины и заказа.

### TC-API-CART-02. Добавление недоступного товара отклоняется

**Покрывает:** CL-API-CART-2, Q-17, критерий приёмки | **Приоритет:** P0

**Предусловия:** корзина сессии `S1` пуста, известен `{id_cheesecake}`.

**Шаги:**

1. Выполнить `POST /shop/cart` с `{id_cheesecake}` и количеством 1.

3. Выполнить `GET /shop/cart` и проверить состав.

**Ожидаемый результат:** запрос отклонён клиентским кодом ошибки, ожидаемо 422 с JSON-описанием; корзина остаётся пустой.

**Обоснование:** дословный критерий приёмки, проверяемый в обход UI. Если барьер реализован только на клиенте, заказ недоступного товара создаётся любым прямым запросом.

### TC-API-CART-03. Получение корзины текущей сессии

**Покрывает:** CL-API-CART-3 | **Приоритет:** P0

**Предусловия:** в корзине сессии `S1` две позиции с известными ценами и количествами.

**Ожидаемый результат:** код 200, состав позиций соответствует добавленным товарам, сумма товаров равна сумме произведений цены на количество, расчётные поля присутствуют.

**Обоснование:** корзина API — единственный источник данных для UI и для суммы заказа. Ошибка в её расчётах распространяется на все остальные уровни.

### TC-API-CART-04. Изменение количества внутри допустимого диапазона

**Покрывает:** CL-API-CART-4, Q-15 | **Приоритет:** P0

**Предусловия:** в корзине сессии `S1` Товар A в количестве 1.

**Шаги:** выполнить `PATCH /shop/cart/{id_A}` с количеством из таблицы, затем проверить код ответа и корзину.

| Вариант | Количество | Ожидаемый результат |
|---|---|---|
| 1 | 1 | количество 1 |
| 2 | 10 | количество 10 |
| 3 | 20 | количество 20 |

**Ожидаемый результат:** во всех вариантах возвращается успешный код (ожидаемо 200), количество в корзине соответствует запросу, сумма товаров пересчитана.

**Обоснование:** нижняя и верхняя допустимые границы диапазона 1–20. Код успешного ответа `PATCH` не зафиксирован требованиями (Q-15), поэтому кейс закрепляет фактический контракт.

### TC-API-CART-05. Изменение количества на недопустимое значение отклоняется

**Покрывает:** CL-API-CART-5, CL-API-CART-6, CL-API-CART-7, Q-16 | **Приоритет:** P0

**Предусловия:** в корзине сессии `S1` Товар A в количестве 5.

**Шаги:** выполнить `PATCH /shop/cart/{id_A}` со значением из таблицы, проверить код ответа, тело ошибки и состояние корзины.

| Вариант | Количество | Ожидаемый результат |
|---|---|---|
| 1 | 21 | 422, JSON с описанием ошибки |
| 2 | -1 | 422, JSON с описанием ошибки |
| 3 | `abc` | клиентский код ошибки, ответ 5xx недопустим |
| 4 | отсутствует в теле | клиентский код ошибки, ответ 5xx недопустим |

**Ожидаемый результат:** ни один вариант не изменяет корзину, количество остаётся равным 5, ошибки возвращаются в JSON-формате.

**Обоснование:** требование ограничивает количество диапазоном 1–20, а формат ошибок валидации — статусом 422. Превышение верхней границы через прямой запрос создаёт заказ, который магазин не сможет исполнить.

### TC-API-CART-06. Изменение количества на 0 удаляет позицию

**Покрывает:** CL-API-CART-8 | **Приоритет:** P1

**Предусловия:** в корзине сессии `S1` Товар A в количестве 3.

2. Проверить код ответа.

**Ожидаемый результат:** запрос выполнен успешно, позиция удалена из корзины, расчётные значения обнулены.

**Обоснование:** правило удаления при нуле задано для корзины в целом и должно действовать на обоих уровнях. Позиция с количеством 0 в данных искажает сумму заказа и отображение UI.

### TC-API-CART-07. Удаление товара из корзины

**Покрывает:** CL-API-CART-9, CL-API-CART-10, Q-15 | **Приоритет:** P0

**Предусловия:** в корзине сессии `S1` Товар A.

**Шаги:**

1. Выполнить `DELETE /shop/cart/{id_A}` и проверить код ответа.
2. Выполнить `GET /shop/cart` и проверить состав.
3. Выполнить `DELETE /shop/cart/{id_A}` повторно для уже отсутствующей позиции.
4. Проверить код ответа второго запроса.

**Ожидаемый результат:** первый запрос успешен (ожидаемо 200 или 204), позиция удалена. Повторный запрос возвращает успешный код или 404, ответ 5xx недопустим.

**Обоснование:** код успешного ответа `DELETE` требованиями не задан (Q-15). Повторное удаление проверяет устойчивость: клиент может отправить запрос дважды при потере соединения.

### TC-API-CART-08. Повторное добавление товара и превышение лимита при добавлении

**Покрывает:** CL-API-CART-11, CL-API-CART-12 | **Приоритет:** P1

**Предусловия:** корзина сессии `S1` пуста.

**Шаги:**

1. Выполнить `POST /shop/cart` с `{id_A}` и количеством 1.
2. Выполнить тот же запрос повторно и проверить код ответа и корзину.
3. Очистить корзину.
4. Выполнить `POST /shop/cart` с `{id_A}` и количеством 21, проверить код ответа и корзину.

**Ожидаемый результат:** повторное добавление увеличивает количество существующей позиции до 2 и не создаёт дубль. Добавление с количеством 21 отклоняется клиентским кодом ошибки, корзина остаётся пустой.

**Обоснование:** требование описывает лимит 1–20 для изменения количества, но не для добавления, что оставляет обход границы через `POST`. Дубль позиции дополнительно позволяет превысить лимит суммой двух позиций одного товара.

### TC-API-ORD-03. Создание заказа без обязательных полей возвращает 422

### TC-API-ORD-04. Корзина очищается после создания заказа

### TC-API-ORD-05. Сумма заказа соответствует расчёту корзины

3. Сравнить сумму в ответе с зафиксированным итогом корзины.

**Ожидаемый результат:** сумма заказа равна итоговой сумме корзины с учётом скидки и стоимости доставки.

**Обоснование:** заказ фиксирует сумму к оплате. Пересчёт по другой формуле в момент создания заказа означает, что пользователь платит не ту сумму, которую видел.

### TC-API-ORD-06. Получение списка заказов сессии

**Покрывает:** CL-API-ORD-6, Q-20 | **Приоритет:** P1

**Предусловия:** в сессии `S1` создан хотя бы один заказ с известным номером.

**Шаги:**

1. Выполнить `GET /shop/orders`.
2. Проверить код ответа и структуру ответа.
3. Найти в списке заказ с зафиксированным номером.

**Ожидаемый результат:** код 200, список содержит созданный заказ с корректной суммой и статусом `created`.

**Обоснование:** поведение эндпоинта не описано требованиями (Q-20), поэтому кейс закрепляет минимальный контракт — созданный заказ должен быть доступен для чтения.

## Изоляция учебных сессий

### TC-API-SESS-01. Корзины разных сессий изолированы

**Покрывает:** CL-SESS-1 | **Приоритет:** P0

**Предусловия:** определены два разных значения `X-Course-Session`: `S1` и `S2`; обе корзины пусты.

**Шаги:**

1. Выполнить `POST /shop/cart` с `{id_A}` и заголовком `X-Course-Session: S1`.
2. Выполнить `GET /shop/cart` с заголовком `X-Course-Session: S2` и проверить состав.
3. Выполнить `POST /shop/cart` с другим товаром и заголовком `S2`.
4. Выполнить `GET /shop/cart` с заголовком `S1` и проверить состав.

**Ожидаемый результат:** корзина `S2` не содержит товар, добавленный в `S1`, и наоборот. Каждая сессия видит только свои позиции.

**Обоснование:** изоляция данных — заявленное назначение заголовка. Без неё параллельные автотесты нестабильны, а результаты ручных прогонов невоспроизводимы.

### TC-API-SESS-02. Заказы разных сессий изолированы

**Покрывает:** CL-SESS-2 | **Приоритет:** P0

**Предусловия:** определены сессии `S1` и `S2`; в корзине `S1` есть доступные товары.

**Шаги:**

1. Создать заказ в сессии `S1` и зафиксировать его номер.
2. Выполнить `GET /shop/orders` с заголовком `X-Course-Session: S2`.
3. Проверить наличие заказа `S1` в ответе.

**Ожидаемый результат:** список заказов сессии `S2` не содержит заказ, созданный в сессии `S1`.

**Обоснование:** заказы содержат персональные данные — имя, телефон и адрес. Их доступность из чужой сессии является утечкой, а не только помехой для тестирования.

### TC-API-SESS-03. Запрос без заголовка сессии не отдаёт чужие данные

**Покрывает:** CL-SESS-3, Q-21 | **Приоритет:** P1

**Предусловия:** в корзине сессии `S1` есть товары.

**Шаги:**

1. Выполнить `GET /shop/cart` без заголовка `X-Course-Session`.
2. Проверить код ответа и тело.
3. Выполнить `GET /shop/orders` без заголовка и проверить ответ.

**Ожидаемый результат:** сервер либо отклоняет запрос клиентским кодом ошибки, либо возвращает пустые данные. Данные сессии `S1` в ответе отсутствуют, ответ 5xx недопустим.

**Обоснование:** обязательность заголовка требованиями не описана (Q-21). Общая корзина по умолчанию означает, что все пользователи стенда работают с одними данными.

## Безопасность API

### TC-API-SEC-01. Сумма заказа не принимается от клиента

**Покрывает:** SEC-3 | **Приоритет:** P1

**Предусловия:** в корзине сессии `S1` товары с известной итоговой суммой.

**Шаги:**

1. Выполнить `POST /shop/orders` с корректными данными и дополнительными полями суммы и скидки, содержащими заниженные значения, например сумма 1 и скидка 100%.
2. Проверить код ответа.
3. Проверить сумму в созданном заказе.

**Ожидаемый результат:** сумма заказа рассчитана сервером по составу корзины и не совпадает с переданными значениями, либо запрос отклонён с ошибкой валидации.

**Обоснование:** расчёт суммы обязан выполняться на сервере. Доверие к клиентским значениям позволяет оформить любой заказ за произвольную сумму, что является прямым финансовым риском.

### TC-API-SEC-02. Чужая корзина недоступна для изменения

**Покрывает:** SEC-4 | **Приоритет:** P1

**Предусловия:** в корзине сессии `S1` Товар A в количестве 2; определена сессия `S2`.

**Шаги:**

1. Выполнить `PATCH /shop/cart/{id_A}` с количеством 20 и заголовком `X-Course-Session: S2`.
2. Выполнить `GET /shop/cart` с заголовком `S1` и проверить количество.
3. Выполнить `DELETE /shop/cart/{id_A}` с заголовком `S2`.
4. Выполнить `GET /shop/cart` с заголовком `S1` и проверить состав.

**Ожидаемый результат:** количество и состав корзины `S1` не изменились. Запросы из сессии `S2` затрагивают только её собственную корзину.

**Обоснование:** проверка горизонтального повышения доступа между сессиями. Возможность изменить чужую корзину означает, что идентификатор товара используется как ключ без привязки к владельцу данных.
